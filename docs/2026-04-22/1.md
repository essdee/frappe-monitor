# Frappe Monitor — Project Plan

A custom monitoring and alerting tool for multi-server, multi-bench, multi-site Frappe deployments. Built as a single Go binary on a dedicated monitoring VM, pulling metrics over SSH, storing in VictoriaMetrics + Loki, with a custom dashboard and email + Telegram alerting.

---

## 1. Goals and Scope

### What this tool is

- A Frappe-native monitoring and alerting system.
- Self-hosted, single-operator-friendly, no cloud dependencies.
- Focused on the Server → Bench → Site hierarchy that Frappe actually uses.
- Custom UI built for the specific workflows (no Grafana).

### What this tool is NOT (v1)

- Not an APM (no per-request tracing, no code-level profiling).
- Not a log aggregation search engine (Loki does that; we only consume it).
- Not a multi-tenant SaaS product.
- Not a replacement for OS-level observability like `htop` or `iotop`.

### Non-goals to resist

- Building a plugin architecture before there's a second plugin.
- Making the agent script pluggable.
- Supporting non-Frappe workloads.
- Kubernetes deployment (single VM is the target).

## 2. Architecture Overview

### The hierarchy

```
Server (machine / VM)
  └── Bench (Frappe installation directory)
        └── Site (Frappe tenant)
```

One server can host many benches. One bench can host many sites. All configuration, metrics, labels, and alerts respect this three-level hierarchy.

### High-level data flow

```
Bench Servers                 Monitoring Server
─────────────                 ────────────────────────────────
                              
[Bench Srv 1] ◄──┐            ┌──────────────────────────────┐
  collect.sh     │            │  monitor-server (Go binary)  │
                 │            │                              │
[Bench Srv 2] ◄──┼── SSH ─────┤  ┌─── SSH Pool ───┐          │
  collect.sh     │  (pull)    │  │ (goroutines)   │          │
                 │            │  └────────┬───────┘          │
[Bench Srv 3] ◄──┘            │           │                  │
  collect.sh                  │           ▼                  │
                              │  ┌─── Parsers ────┐          │
                              │  │ server/bench/  │          │
                              │  │ site/logs      │          │
                              │  └────┬───────┬───┘          │
                              │       │       │              │
                              │       ▼       ▼              │
                              │   [metrics] [logs]           │
                              │       │       │              │
                              └───────┼───────┼──────────────┘
                                      │       │
                                      ▼       ▼
                              ┌──────────┐  ┌──────┐
                              │ Victoria │  │ Loki │
                              │ Metrics  │  │      │
                              └────┬─────┘  └──┬───┘
                                   │           │
                                   └─────┬─────┘
                                         │ PromQL / LogQL
                                         ▼
                              ┌──────────────────────┐
                              │  Go HTTP API layer   │
                              │  (proxies + app API) │
                              └──────────┬───────────┘
                                         │
                                         ▼
                              ┌──────────────────────┐
                              │  Custom Dashboard    │
                              │  (Vue/React SPA)     │
                              │  embedded in binary  │
                              └──────────────────────┘
```

### Components

| Component | Runs on | Purpose |
|---|---|---|
| `monitor-server` (Go binary) | Monitoring VM | Brain: SSH pool, scheduler, parsers, writers, alert engine, HTTP API, embedded SPA |
| VictoriaMetrics | Monitoring VM | Time-series storage, push-friendly, PromQL-compatible |
| Loki | Monitoring VM | Log storage, LogQL queries |
| SQLite | Monitoring VM | Config, current state, alert rules, alert events |
| `frappe-monitor-collect.sh` | Each bench server | One-shot collector script, outputs structured data |

### Why this architecture

- **Bench servers stay untouched** — no daemon, no port opened, no runtime installed beyond a shell script and a restricted SSH user.
- **Single binary for the app** — `scp` + systemd unit, done. No Python/Node/Frappe on the monitoring VM.
- **VictoriaMetrics over Prometheus** — push model matches the SSH-pull architecture without needing Pushgateway or cache-and-expose hacks. Same query language (PromQL), better cardinality handling, simpler operations.
- **Loki for logs** — LogQL is powerful enough for slow query search and error log tailing without running Elasticsearch.
- **Custom SPA owns the UX** — full control over dashboard design, no fighting Grafana plugins.

- **VictoriaMetrics** — official Docker image, accepts Influx line protocol pushes

SQLite is the final, settled choice. Full justification and configuration in section 4 (Data Model). No migration to another DB is planned.

- `victoriametrics` — official image
- `loki` — official image
- `caddy` — reverse proxy + automatic TLS

Single `docker-compose.yml` defines the whole stack. Single `./data/` directory holds all persistent state.

- **Language:** bash (portable, no runtime needed)

## 4. Data Model

### Hierarchy

```
Server (1) ──────< Bench (N) ──────< Site (N)
```

### The `Store` interface

Database access goes through a single `Store` interface in one package. No raw SQL anywhere else in the codebase. This is about clean architecture and testability — not about preparing for a DB migration (which isn't planned).

```go
type Store interface {
    // Servers
    CreateServer(ctx, Server) (Server, error)
    GetServer(ctx, id) (Server, error)
    ListServers(ctx) ([]Server, error)
    UpdateServer(ctx, Server) error
    DeleteServer(ctx, id) error
    
    // Benches, Sites, AlertRules, AlertEvents... same pattern
}

type EntStore struct { client *ent.Client }
```

The rest of the app depends on `Store`, not on ent or SQLite specifically. This keeps the storage layer isolated, makes handler and collector testing trivial (inject a fake store), and prevents ent queries from leaking into business logic. Schema definitions live in `ent/schema/`, and ent-generated code is confined to the storage package.

### Database choice: SQLite (final)

This DB holds servers, benches, sites, alert rules, alert events, and deploy events — a few thousand writes per month with strong relational constraints. The high-volume data (metrics and logs) goes to VictoriaMetrics and Loki and never touches this DB.

**Why SQLite:**
- **Lowest resource footprint** of any option: ~5–10 MB RAM, zero idle CPU, single-file storage in low MB range.
- **Zero operational overhead**: no separate process, no daemon, no tuning knobs to manage.
- **Relational with full ACID**: cascading deletes, joins across the hierarchy, foreign-key integrity, transactions.
- **Scale fits comfortably**: SQLite handles billions of rows; this workload uses <1% of its capacity.
- **Perfect match for the architecture**: single writer (one Go process), single machine, no network DB access needed.

**Why not the alternatives:**
- **Postgres**: ~80–150 MB RAM minimum even tuned, continuous background workers (autovacuum, WAL writer), extra container to operate and back up. Overkill for a few-thousand-row workload.
- **MariaDB/MySQL**: buffer pool behavior is wasteful at this scale; ~150–300 MB minimum.
- **MongoDB**: non-relational; forces application-side joins and manual cascades for no gain. Wrong model for structured data with cascades.
- **DuckDB**: excellent for analytics (OLAP) but not optimized for the frequent small writes this DB needs (OLTP).

**Recommended PRAGMAs at startup:**

```sql
PRAGMA journal_mode = WAL;           -- readers don't block writers
PRAGMA synchronous = NORMAL;         -- good durability, faster than FULL
PRAGMA busy_timeout = 5000;          -- wait 5s on lock contention
PRAGMA foreign_keys = ON;            -- enforce cascades
PRAGMA temp_store = MEMORY;          -- temp tables in RAM
PRAGMA mmap_size = 134217728;        -- 128MB memory-mapped I/O
PRAGMA cache_size = -64000;          -- 64MB page cache
```

These settings tune SQLite for a server-like workload while keeping total DB resource usage well under 100 MB.

**Migration plan: none planned.** If hypothetically outgrown in the future, the `Store` interface pattern keeps migration to Postgres to a weekend of work. No migration to a document store will ever make sense for this data model.

### Tables (conceptual — schema design deferred to implementation phase)

- **servers** — hostname, SSH connection details, status, labels
- **benches** — server link, name, path, Frappe version, apps, Redis ports, status
- **sites** — bench link, name, URL, DB name, thresholds overrides, status
- **ssh_credentials** — encrypted key/password storage
- **alert_rules** — metric, operator, threshold, duration, scope (server/bench/site), notification channels, severity
- **alert_events** — rule link, scope snapshot, status (firing/ack/resolved), timestamps, trigger value
- **deploy_events** — logged from CI/CD, used for overlay markers on graphs
- **log_cursors** — byte-offset tracking per log file per bench for incremental tailing
- **notification_channels** — SMTP config, Telegram bot config, default recipients

Cascading deletes: removing a server cleans up its benches, sites, and their alert events.

### Metric naming convention

```
frappe_server_<metric>{server="..."}
frappe_bench_<metric>{server="...", bench="..."}
frappe_site_<metric>{server="...", bench="...", site="..."}
```

Every metric carries the full hierarchy as labels. This keeps `client-a.com` on `production-bench` distinct from `client-a.com` on `staging-bench` even when the domain name collides.

## 5. The Collection Layer

### Pull model

The monitoring server SSHes into each bench server on a schedule (default 15 min, configurable per server). No agent runs continuously on bench servers.

### The one-shot collector script

Deployed once to each bench server at `/usr/local/bin/frappe-monitor-collect.sh`. Version-headered — monitoring server checks the version each pull and redeploys on mismatch.

Script outputs structured, sectioned text:

```
###META
version=1.0.0
timestamp=<unix>
hostname=<name>

###SERVER
<CPU, memory, disk, load, uptime>

###BENCH:<bench_name>
<path, frappe version, apps, redis ports, queue depths, supervisor status>

###SITE:<bench_name>:<site_name>
<db name, health status, response time, file storage, sessions>

###END
```

One SSH call per server returns metrics for the server plus all benches plus all sites. Go parser splits on `###` markers and routes sections to typed parsers.

### What's collected

**Server level (every pull):**
- CPU usage (from `/proc/stat`)
- Memory (from `/proc/meminfo`)
- Disk usage per mount (from `df`)
- Load averages (from `/proc/loadavg`)
- Network I/O (from `/proc/net/dev`)
- Uptime

**Bench level (every pull):**
- Frappe version
- Installed apps + current git commits
- Redis queue depths (short / default / long / failed)
- Supervisor process states (gunicorn, scheduler, workers)
- Redis memory usage

**Site level (every pull):**
- Health check (HTTP status + response time via `/api/method/ping`)
- Database size (from `information_schema.tables`)
- Active sessions count
- File storage size (public + private) — every few hours, not every pull
- Error count in last pull window

**Logs (every 5 min):**
- Tail of `web.error.log`, `worker.error.log`, `schedule.error.log` per bench
- MariaDB slow query log (with `long_query_time = 1` configured)
- Tracked via byte offsets in a `log_cursors` table for incremental reads

### Concurrency model

- One goroutine per server, bounded by a semaphore (default: 10 parallel servers).
- SSH connections pooled and reused across pulls (not reconnected every cycle).
- Per-server timeout (30s default) so one slow server doesn't block others.
- Context-based cancellation propagates through the entire pull.

## 6. The Storage Layer

### Split of responsibilities

| What | Where | Why |
|---|---|---|
| Numeric time-series (CPU %, response time, queue depth) | VictoriaMetrics | Purpose-built for this; PromQL queries |
| Logs and slow queries | Loki | LogQL search, label-based filtering |
| Config (Server / Bench / Site definitions) | SQLite | Relational, Frappe-style CRUD needed |
| Current state snapshot (last-known status) | SQLite | Fast dashboard reads without hitting VM |
| Alert rules + events | SQLite | Relational, needs transactions |
| Deploy events | SQLite | Joined with graphs as overlays |

Don't mix. No time-series in SQLite (bloat). No config in VictoriaMetrics (wrong tool).

### VictoriaMetrics push protocol

Use Influx line protocol for writes:
```
frappe_site_response_time_ms,server=prod-1,bench=production-bench,site=client-a.com value=234.5 <timestamp_ns>
```

Batch all metrics from one pull cycle into one HTTP POST per server. Avoid per-metric writes.

### Loki push protocol

JSON POST to `/loki/api/v1/push`. Group log lines by label set (same `{server, bench, site, log_type}` = same stream) before pushing. Keep high-cardinality data (user IDs, request IDs) in the log line itself, not in labels.

### Retention policy

Decide before collecting a single byte. Suggested starting point:

- **VictoriaMetrics:** 90 days raw, configurable via `-retentionPeriod` flag.
- **Loki:** 30 days raw, configurable in `loki-config.yaml`.
- **SQLite alert_events:** 1 year, archived older.
- **SQLite log_cursors, current status:** no retention (always overwritten).

### Auth

- Session cookies for SPA users, backed by bcrypt-hashed passwords in SQLite.
- API tokens for CI/CD integrations (deploy events).
- SPA served from same origin — no CORS headaches.
- VictoriaMetrics and Loki never exposed to browsers; always proxied through Go API.

### Proxy endpoints (important)

The `/api/v1/metrics/query` and `/api/v1/logs/query` endpoints proxy to VictoriaMetrics and Loki respectively. This keeps backend URLs private, enforces auth, and lets you add caching/rate-limiting later without touching the frontend.

## 9. The Alert System

### Design

Alert rules scoped at any level: global, server, bench, or site. One rule schema supports all scopes via nullable scope fields.

### Rule structure

- **Metric** — which metric to watch (e.g. `frappe_site_response_time_ms`)
- **Operator** — gt / lt / gte / lte / eq
- **Threshold** — numeric value
- **Duration** — must breach for this long (default 5 min)
- **Scope** — nullable server_id / bench_id / site_id (all null = global)
- **Severity** — info / warning / critical
- **Notifications** — email yes/no, Telegram yes/no, per-rule recipient overrides

### Evaluation engine

Runs every minute independently of the collection schedule:

1. For each enabled rule, build a PromQL query with scope filters applied.
2. Use `avg_over_time(metric[duration])` or similar to enforce the duration requirement within the query itself.
3. Query returns zero or more breaching series (each identified by its full label set).
4. For each breach, check `alert_events` for an open event with the same rule + label set.
   - None: create event, fire notification.
   - Exists: do nothing (already firing).
5. For previously firing events no longer in results: mark resolved, fire recovery notification.

### Default rule set (ships with v1)

- Server unreachable for > 3 pull cycles → critical
- CPU > 90% for 10 min → warning
- Memory > 90% for 10 min → warning
- Disk > 85% → warning, > 95% → critical
- Site health check failing for 3 min → critical
- Site p95 response time > 3s for 10 min → warning
- Redis long queue > 500 → warning, > 2000 → critical
- Scheduler not running for > 5 min → critical
- Any worker process dead for > 5 min → critical
- MariaDB connections > 80% of max → warning

### Cooldown and flapping protection

- **Cooldown:** after firing+resolving, suppress re-fires of the same rule + scope for N minutes (default 15).
- **Grouping window:** notifications fired within 30 seconds of each other get bundled into one message (prevents 20 Telegram messages when DB dies).

Implement both in the notifier layer, not the evaluation engine.

### Notification channels

**Email (via SMTP)**
- Use a real SMTP provider (SES, Postmark, Resend) — not Gmail — for reliable delivery
- HTML template: severity color, scope hierarchy, metric, current value, threshold, link to dashboard
- Default recipients list + per-rule overrides

**Telegram (via Bot API)**
- Create bot via `@BotFather`, store bot token
- Support multiple chat IDs (personal, team channel, per-client)
- Message format: severity emoji + scope + metric value + dashboard link
- Use `parse_mode: HTML` to avoid MarkdownV2 escape pain

### Routing defaults

| Severity | Email | Telegram | Notes |
|---|---|---|---|
| Critical | Yes, immediate | Yes, immediate | No grouping delay |
| Warning | Digest every hour if unresolved | Yes, grouped 30s | |
| Info | No | Yes, grouped 30s | |
| Recovery | Same as original | Same as original | Simpler message |

## 10. Deployment

### Docker Compose on a single VM

Everything runs in containers. The only thing installed on the host is Docker itself.

| Container | Image | Purpose | Exposed |
|---|---|---|---|

### SQLite in Docker — one thing to know

- Enable WAL mode (`PRAGMA journal_mode=WAL`) at startup for better concurrency.
- Keep the SQLite file on local disk (bind mount). Never on NFS — file locking breaks.

### Bench servers (each)

One-time setup, unchanged from before:

1. Create dedicated `monitor` user.
2. Add monitoring server's SSH public key to `~/.ssh/authorized_keys`.
3. Add restricted sudoers entry: only specific commands the collector needs.
4. Deploy `/usr/local/bin/frappe-monitor-collect.sh` (done by monitoring server via its API).
5. Enable MariaDB slow query log with `long_query_time = 1`.

### Self-monitoring

- External uptime check pinging `https://monitor.yourdomain.com/healthz` every minute (UptimeRobot free tier).
- The Go binary exposes its own `/metrics` endpoint — collection success rate, SSH failure count, alert evaluation time. Graph these inside the tool itself.
- Separate alert: if no collection cycle has completed in 2× the interval, page.

### Backup

One directory: `/opt/frappe-monitor/data/`. Nightly snapshot (or `restic`, `borgbackup`, rsync to object storage).

For VictoriaMetrics specifically, use `vmbackup` for consistent snapshots instead of copying files while the container runs. Run it as a one-shot container on a schedule.

SSH keys and the `.env` file are not in `data/` — back those up separately to a password manager or secrets vault.

## 11. Security Considerations

### SSH

- Dedicated `monitor` user on each bench server — never root.
- Restricted sudoers file listing only needed commands (reading logs, running specific `bench` commands).
- ED25519 keys, not RSA.
- Key per environment (staging keys ≠ production keys).
- Key passphrase stored in monitoring server env var, not in SQLite.

### Credential storage

- SSH private keys and SMTP passwords encrypted at rest using a master key from env var.
- Master key never committed to git, never logged.
- Key rotation procedure documented.

### Application auth

- Session cookies with `HttpOnly`, `Secure`, `SameSite=Strict`.
- Passwords hashed with bcrypt (cost factor 12+).
- Rate limiting on login endpoint.
- CSRF tokens on mutating endpoints.

### Network

- VictoriaMetrics and Loki bound to `127.0.0.1` only — only the Go binary on localhost talks to them.
- Monitoring dashboard behind TLS (Let's Encrypt via Caddy — see section 10).
- Optional: VPN-only access to the monitoring dashboard.

### Audit

- Log all config changes (who added server X, who changed alert rule Y).
- Log all acknowledged alerts (who ack'd, when, optional comment).

## 13. Things to Decide Upfront

These are hard to change later:

- **Pull interval per server.** Default 15 min but allow per-server override. Don't go below 5 min over SSH.
- **Retention policy.** Decide now. "Keep everything" is not a policy.
- **Timezone.** Store all timestamps in UTC. Convert on display only.
- **Multi-tenant or single.** Are other people logging in with scoped access? Design access control now if yes.
- **Collector script versioning.** Always send a version header. Reject pulls from unknown versions.
- **Graceful degradation.** If VM or Loki is down, buffer writes to disk, don't drop data.
- **Clock skew.** Servers with wrong clocks produce bad data. Log received-at time as fallback.

## 14. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Monitoring server goes down silently | External uptime check + self-monitoring metrics |
| SSH pool exhausts connections | Bounded semaphore, connection TTL, graceful reconnect |
| One slow server blocks collection | Per-server timeout, goroutine isolation |
| Metric cardinality explosion | Labels audited; no user IDs or request IDs in labels |
| SQLite lock contention at scale | Single-writer pattern, WAL mode enabled |
| Alert storms during incidents | Cooldown + grouping window in notifier |
| Collector script breaks on Frappe upgrade | Version the script, test against staging first |
| SSH keys compromised | Per-environment keys, rotation procedure, audit log |
| Disk fills up from metrics/logs | Retention policies + disk alerts on the monitor itself |

## 15. Success Criteria

The initial release is done when:

- Adding a new server takes under 5 minutes (add via UI → deploy collector via API → metrics appear).
- Site-level p95 response time is graphable with deploy markers overlaid.
- A site going down triggers a Telegram message within 3 minutes.
- An ack'd alert disappears from the active alerts view.
- The slow query feed for any site is searchable by duration threshold.
- The monitoring server runs unattended against real production traffic with no crashes or manual restarts.
- Backups have been tested by doing a full restore to a staging VM.

## Appendix B — Useful PromQL Queries (reference)

```promql
# Server CPU % averaged over 5 min
avg_over_time(frappe_server_cpu_percent[5m])

# Site p95 response time
histogram_quantile(0.95, 
  rate(frappe_site_response_time_ms_bucket[5m]))

# Sites currently down
frappe_site_health_status != 200

# Redis long queue growing
deriv(frappe_bench_queue_depth{queue="long"}[10m]) > 0

# Disk full prediction (days until 100%)
predict_linear(frappe_server_disk_used_bytes[6h], 86400 * 7)
```
