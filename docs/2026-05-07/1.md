# Telegram alert message redesign

## Problem

The Phase 6 Telegram message format was strictly functional:

```
[CRITICAL] RuleName
RuleName {bench=foo,server=bar,site=baz} value=92.4123
```

Operator feedback: "very normal, not attractive, not in standard way." The
text carried all the right facts but presented them as a debug dump rather
than an alert. The label-set blob `{bench=...,server=...}` is a useful
machine-readable form for the API but is the wrong shape for a phone push.

## Decision

Rewrite `formatMessage` in `internal/alerts/telegram.go` to render an
HTML card with three visual zones:

1. **Headline** — severity emoji + bolded severity word + rule name in italics.
2. **Body** — the rule's `Message` template output, bolded as the focal point.
3. **Footer** — derived breadcrumb (`server → bench → site`, only the
   levels present in the firing labels) + verb (`fired` / `cleared`) +
   wall-clock timestamp in `<code>`.

Firing (critical):

```
🚨 <b>CRITICAL</b> — <i>site_unhealthy</i>

<b>Site "client-a.com" on prod-1/production-bench is unhealthy.</b>

prod-1 → production-bench → client-a.com
<code>fired 21:14 IST</code>
```

Resolved (any severity):

```
✅ <b>RESOLVED</b> — <i>site_unhealthy</i>

<b>Site "client-a.com" on prod-1/production-bench is unhealthy.</b>

prod-1 → production-bench → client-a.com
<code>cleared 21:18 IST</code>
```

Icons: `🚨 critical`, `⚠️ warning`, `ℹ️ info`, `✅ resolved` (always green for
resolved, regardless of original severity — calmer-than-fire even for what
used to be a critical).

## Interface change

The `Notifier.Notify` signature changed from
`(ctx, severity, ruleName, message string)` to `(ctx, Notification)` where
`Notification` carries `{Severity, RuleName, Body, Labels, Resolved, Time}`.
This was needed so the breadcrumb could be derived from the firing
sample's labels rather than hand-built into every rule template.

The `Rule.Message` template surface is unchanged. Operators write the
same `"Site \"{{.Labels.site}}\" on {{.Labels.server}}/{{.Labels.bench}}
is unhealthy."` template they always have; the new framing wraps it.

The legacy `" RESOLVED"` suffix on the rule name is gone — the resolved
state is now carried by the `Resolved bool` field, which lets the
formatter render `✅ RESOLVED` as the headline instead of mutating the
rule identifier.

## Why HTML, not MarkdownV2

Telegram MarkdownV2 has aggressive escape rules — every `.`, `-`, `(`,
`!` etc. must be backslash-escaped or the entire message rejects with
400. HTML mode escapes only `<`, `>`, `&` — vastly easier to keep right
when label values can carry punctuation (hostnames, FQDNs, file paths).
HTML mode was already what the previous formatter used; we kept it.

## Why a breadcrumb derived from labels (not from each rule's template)

The body sentence already mentions the relevant entities ("Site X on
Y/Z is unhealthy"), but having a separate, deterministic breadcrumb
line means:

- Cards look uniform regardless of how each rule's `Message` is phrased.
- A glance lands on the affected scope before reading the sentence.
- Custom rules that forget to mention `{{.Labels.server}}` still
  produce a card that says where the alert came from.

Only `server`, `bench`, `site` labels are picked, in that order. Other
labels (`mount`, `queue`, etc.) stay in the body where the rule's
template can phrase them naturally — adding them to the breadcrumb
would make queue/disk alerts feel inconsistent with site/health alerts.

## Resolved messages always look "calm"

A resolved critical and a resolved warning both render as `✅ RESOLVED`
— same icon, same colour intent. The point of the resolve message is
"this is over"; preserving the firing severity in the resolved card
sends a confused signal. The footer still carries the rule name and
breadcrumb so operators can correlate it with the original fire.

## Tests

- `TestTelegram_PostsToSendMessage` — body+headline+footer present.
- `TestTelegram_ResolvedLooksDifferent` — RESOLVED + ✅ + cleared, no
  CRITICAL/🚨 leakage.
- `TestTelegram_BreadcrumbDerivedFromLabels` — server→bench→site joined
  with arrows when all three labels exist.
- `TestTelegram_BreadcrumbOmittedWhenNoHierarchyLabels` — no arrow when
  none of `server/bench/site` are present.
- `TestFormatMessage_EscapesUntrustedFields` — `<script>` in rule name
  or label values gets escaped; our own `<b>` tags survive.
- `TestFormatMessage_FallbackBodyWhenEmpty` — a rule with an empty
  rendered message still produces a useful card.

Existing evaluator tests updated for the new `Notification` struct;
fire-vs-resolve disambiguation moved from suffix-matching the rule
name to checking the `resolved` flag on the recorded call.

## Out of scope

- Per-rule custom icons (could be added via `Rule.Icon` later, low value
  given the four severity icons cover the cases).
- Threshold + delta in the headline (would require carrying threshold
  through the rule, doable but larger surface — defer until requested).
- Dashboard deep-links inside the message (no public URL is configured
  in `monitor.yaml` today; revisit when an operator wires Caddy in front
  with a stable hostname).
