# Phase 8 — Per-event capture: queries, API calls, errors

## Goal

Move from "every-15-minutes sampled state" to **per-event capture** of:

1. Every HTTP / API call hitting any Frappe site
2. Every slow SQL query (with full text, attributed to the site)
3. Every Python error from web, worker, scheduler

Each event is attributed to its `{server, bench, site}` triple. Operator
answers we want to enable:

- "Which sites have the most slow queries right now?"
- "Which endpoints are erroring on which sites? Top 10."
- "Error rate and request rate per site over the last hour."
- "Tail of recent slow queries on `client-a.com` filtered by duration."

## Constraints (both firm)

1. **Zero impact on bench-server performance.** This rules out anything
   that adds CPU per request, takes memory while idle, or holds disk I/O.
2. **No daemon on bench, no port opened, no runtime installed beyond
   bash.** The "untouched bench" rule from the master plan
   (`docs/2026-04-22/1.md:102`) still holds.

The first constraint is the binding one this phase — it is what
determines the architecture choice.

## Decision

**Long-lived SSH session per bench server**, running a companion bash
script `frappe-monitor-stream.sh` that does `tail -F` over a known set
of log files Frappe and MariaDB **already write**. Lines stream back
over SSH stdout. The monitor parses, splits, and pushes:

- **numeric** (rps, latency histograms, query duration, error counters) → VictoriaMetrics
- **text** (full request line, full SQL for slow queries, full
  tracebacks) → Loki

This is an **evolution** of the existing log-tailing path — the
`internal/collector/logtail.go` cursor model and the `log_cursors`
SQLite table already do this on a per-pull basis. Phase 8 keeps the
exact same trust model and cursor logic but switches the SSH session
from "open, run script, close" to "open, run streamer, hold open".

### Why not the alternatives (one line each)

- **Push agent on bench (Vector/Promtail/OTel):** breaks constraint #2,
  adds an upgrade plane on every bench, real RAM cost.
- **Frappe-side instrumentation (`before_request` hooks, Recorder):**
  breaks constraint #1 — every API call pays runtime overhead.
- **MariaDB general query log:** ~30% overhead documented; immediate
  constraint-#1 violation.
- **15-minute pull at higher frequency:** SSH reconnect storm, still
  loses sub-minute events. Doesn't actually solve the problem.

## What gets captured

All sources are files Frappe / MariaDB / the OS already write. **No
new logging is enabled by default** except the slow query log at a
deliberately conservative threshold.

| File | What we extract | Bench cost |
|---|---|---|
| `frappe-bench/logs/web.log` | timestamp, site, method, path, status, ms | none — Frappe writes this anyway |
| `frappe-bench/logs/web.error.log` | full traceback | none — Frappe writes this anyway |
| `frappe-bench/logs/worker.error.log` | full traceback | none — Frappe writes this anyway |
| `frappe-bench/logs/schedule.error.log` | full traceback | none — Frappe writes this anyway |
| MariaDB slow query log | query, db_name, duration, rows_examined | `long_query_time=0.5` default — MariaDB documents <0.1% overhead at this threshold |

Explicitly **not** captured (constraint #1 violations):

- ❌ MariaDB general query log
- ❌ `long_query_time = 0` (= every query into slow log)
- ❌ Frappe Recorder
- ❌ Custom Frappe `before_request` hooks
- ❌ tcpdump / eBPF / strace anywhere on the bench

## Bench-server impact analysis

What runs on the bench during streaming:

- 1 × bash process (the streamer script)
- 1 × `tail -F` process per file (~5 files = 5 procs, all idle except on inotify wake)

Steady-state cost on a typical bench (4 vCPU, 8 GB):

| Resource | Cost |
|---|---|
| CPU | < 0.1% (kernel inotify, almost nothing in userspace) |
| RAM | < 5 MB (bash + tail's read buffers) |
| Disk I/O | **zero** (lines come from page cache, no new reads from disk) |
| Disk space | zero (we read existing files; we don't create new ones) |
| Network out | proportional to log volume — typical site at 500 req/min produces ~5 KB/s |

The only on-bench knob we change is the MariaDB slow query log
threshold, and only when the operator opts in. At `long_query_time=0.5`
this is below the noise floor of normal MariaDB workloads.

## Cardinality plan (the part that matters most)

The kill-switch on a system at this volume is metric label cardinality.
Discipline:

**VictoriaMetrics labels — strict allow-list:**

| Series | Allowed labels |
|---|---|
| `frappe_site_request_count_total` (counter) | `server, bench, site, endpoint_class, status_class` |
| `frappe_site_request_duration_ms` (histogram) | `server, bench, site, endpoint_class` |
| `frappe_site_error_count_total` | `server, bench, site, error_class` |
| `frappe_site_query_duration_ms` (histogram) | `server, bench, site` |
| `frappe_site_slow_query_count_total` | `server, bench, site` |

`endpoint_class` is **not** the raw URL path. Raw paths explode (each
unique `/api/method/some.module.method/<doc>` becomes a series). We
collapse to ~50 buckets max:

- `desk` (`/app/...`)
- `api/method/<module>` (group by Frappe module, ~20 modules)
- `api/resource/<doctype-class>` (group by core/contrib/custom)
- `assets`
- `other`

`status_class`: `2xx | 3xx | 4xx | 5xx`. 4 values, period.

`error_class`: stable Python exception family (`OSError`, `ValidationError`,
`TimestampMismatchError`, …) — bounded by Frappe's exception hierarchy,
not user input.

**Forbidden in labels** (always go in the log line body, never in labels):

- raw URL path / query string
- `user_id` / session id / request id
- `doctype` name (per-tenant, unbounded)
- SQL text or SQL hash
- IP address
- arbitrary user-agent

Estimated steady-state series count for 200 sites × 50 endpoint
buckets × 4 status buckets = ~40k active series. Comfortable headroom
for VM on a 4 vCPU / 8 GB monitor host.

**Loki stream labels — even stricter:**

Only `{server, bench, site, log_type}` where `log_type ∈ {access, error, slow_query}`.
Everything else lives in the line body as JSON the LogQL pipeline can
parse on-demand. This matches what the master plan already documented
(`docs/2026-04-22/1.md:343`).

## Connection management

- **1 SSH conn per server**, held open by the monitor.
- **Reconnect with backoff:** 1s → 2s → 4s → 8s → 16s → 30s → 60s, capped.
- **Resume cursor:** per `(server, file_path)` byte offset in SQLite —
  the `log_cursors` table already has this schema. Reuse, don't add.
- **File rotation:** on reconnect, if the live file's size < cursor,
  read `<file>.1` from cursor → end first, then resume the live file.
  Logrotate's default 7-day retention covers any plausible disconnect.
- **Health metric:** `frappe_stream_connected{server}` (0/1 gauge) and
  `frappe_stream_lag_seconds{server}` (gauge from latest line ts).
- **Default alert rule:** `frappe_stream_connected == 0` for > 2 min.

## Streamer protocol (bench → monitor)

The streamer script multiplexes N tailed files into one stdout stream
with a per-line file marker, so the monitor can route each line to its
parser without N separate SSH sessions:

```
##F=web ##L=2026-05-07T14:21:03.123Z ##S=4231 site_name 192.0.2.10 - "GET /api/method/foo HTTP/1.1" 200 1234 ...
##F=err ##L=2026-05-07T14:21:04.001Z ##S=4789 ValidationError: ...
  File "/home/...", line 42, in ...
##F=slowq ##L=2026-05-07T14:21:04.500Z ##S=5123 # User@Host: ...
##F=slowq # Query_time: 1.231 ...
##F=slowq SELECT ...
```

`##F=` = file id, `##L=` = parsed timestamp from the line, `##S=` =
byte size so the monitor can advance the cursor without trusting the
parser's internal counting. Multi-line records (tracebacks, slow query
blocks) repeat the same `##F=` prefix; the parser joins on
`##L=`-changes.

The protocol is intentionally line-prefixed (not a binary framing
format) so an operator can `ssh bench frappe-monitor-stream.sh` by
hand to debug.

## Implementation plan — sub-phases

Each sub-phase is one reviewable PR via the
`tasks/task-N.md` ↔ `task-N.result.md` workflow.

**8a — Streamer script + protocol.**
- `scripts/frappe-monitor-stream.sh` (bash, embedded into binary).
- Multiplexed `tail -F` with the protocol above.
- Resume from byte offset (passed in via `--resume web=12345,err=678,...`).
- Version header in line 1 of stdout (mismatch = monitor redeploys).
- Smoke: spin up a fake server with seeded log files; assert the
  protocol bytes round-trip.

**8b — Streamer driver in monitor.**
- New `internal/streamer/` package.
- `Manager` owns 1 goroutine per server. Per goroutine: open SSH,
  exec streamer, read stdout, parse lines, fan out to existing VM /
  Loki clients, advance log_cursors transactionally per batch.
- Reconnect / backoff / rotation handling.
- New typed metrics (`frappe_site_request_count_total` etc.) emitted
  with strict label allow-list — wrap the VM client with a "label
  guardrail" check that drops + warns on disallowed labels.

**8c — Default alert rules using new metrics.**
- `site_high_error_rate`: `frappe_site_error_count_total / frappe_site_request_count_total > 0.05` for 5m → critical.
- `site_p95_latency_degraded`: `histogram_quantile(0.95, …) > 3000` for 10m → warning.
- `frappe_stream_disconnected`: `frappe_stream_connected == 0` for 2m → critical.

**8d — Dashboard surfaces.**
- Site detail: live request rate, error rate, p95 latency, slow query
  rate (4 small graphs at the top).
- New "Activity" tab on site detail: scrollable feed of recent errors
  + recent slow queries (LogQL-backed, filterable by class / duration).
- Sites overview table: add columns for last-hour error rate +
  request rate, sortable.

## Operator prerequisites (one-time per bench)

Documented in the deployment guide when 8b lands:

1. Slow query log readable by the SSH user. Typically:
   ```
   chmod g+r /var/log/mysql/mariadb-slow.log
   usermod -a -G adm frappe-monitor   # 'adm' usually has log read perms
   ```
2. `long_query_time = 0.5` in `/etc/mysql/conf.d/frappe.cnf` (or wherever
   the bench config lives). Optional — operators can leave their
   existing threshold.
3. Logrotate keeps `web.log.1`, `mariadb-slow.log.1` for ≥ 24h
   (default on most distros — verify, don't change).

## Failure domains

| Failure | Effect |
|---|---|
| Bench network blip < 60s | Streamer reconnects with offset, no data lost. |
| Bench network blip 60s – 24h | Reconnect resumes from offset; if file rotated, read `<file>.1` then resume. |
| Bench reboots | Streamer reconnects when SSH is back; file content may have rolled over — accept gap, alert via `frappe_stream_lag_seconds`. |
| Monitor restarts | Streamer goroutines re-launched on boot from the cursor table. |
| MariaDB slow log unreadable | Just that file's tail goes silent; access + error streams still work. Surface as a per-file `frappe_stream_file_ok` gauge. |
| VM / Loki down | Same as today: lines buffered briefly, push retried, eventual data loss if downtime > buffer. Phase 8 doesn't change the existing failure semantics here. |

## Backout

If streaming proves operationally bad for some bench, the
**existing 15-minute SSH-pull collector keeps working** — they're
independent code paths. Per-server config flag `streaming.enabled`
defaults to `false`; operators opt in. The dashboard shows whichever
path has data.

## Out of scope (deliberately deferred)

- Distributed tracing across the request path. Would need Frappe
  instrumentation = constraint #1 violation.
- Per-user behavioural telemetry (cursor moves, click events). User
  mentioned this earlier; it's a separate scope (RUM, not monitoring)
  and gets its own design doc when prioritised.
- Replaying the historical Phase 1–7 metrics in the new schema.
  We accept that the new metric families start producing data the day
  Phase 8b lands.
- A live "request waterfall" view per request. Would need request IDs
  in labels — cardinality non-starter.

## What this is *not* solving

It is worth being honest:

- We are **not** capturing every SQL query — the user explicitly
  accepted that "slow queries fully + everything as counts only" is
  the right tradeoff. Constraint #1 wouldn't allow more.
- We are **not** going to give per-user activity timelines from this
  data alone. The line body has user IDs but they're never in labels,
  so PromQL queries can't filter on them. Loki LogQL can — that's the
  intended path.
- We are **not** building a debugger. Errors and slow queries are
  symptoms; correlating them across requests requires request IDs the
  bash streamer can't synthesize without Frappe-side help.

These are honest tradeoffs constraint #1 forces. If they're ever
unacceptable, Phase 9 would re-open the daemon-on-bench question.
