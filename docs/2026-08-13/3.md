# Read-only monitoring product redesign

Date: 2026-08-13  
Branch: `main`

## Product boundary

Frappe Monitor is observability software, not an operations or deployment
tool. Monitored targets are inspected through SSH and must never be changed by
the monitor. The redesign therefore removed the remote collector deployment
route and all deploy/manual-collection/edit/delete controls from the monitoring
UI. Embedded collectors, discovery, and streaming run through `bash -s` over
SSH stdin and leave no target-side files or agents.

Monitor-local registry APIs remain available for installation automation. They
change only SQLite connection metadata; they do not execute a remote mutation.

## Monitoring model

The collector now captures the failure domains operators need when a Frappe
server stops serving requests:

- server CPU, memory, swap, load, disk, network, uptime, and processes;
- bench framework/app inventory and configured web/background-worker capacity;
- Supervisor group state plus the actual matching bench process tree;
- per-service state, PID, type/queue, CPU, memory, RSS, and uptime;
- Redis queue depth and exact RQ registered/busy/idle occupancy;
- site reachability, HTTP status, latency, and stable failure reason;
- standard bench/site log discovery and resumable Loki streaming.

Configured Gunicorn capacity and observed process capacity are kept distinct
from RQ busy/idle state. Stock Gunicorn does not expose an accurate
request-by-request free/busy value through process inspection, so the monitor
does not claim false precision. RQ does expose occupancy through Redis and is
reported exactly.

## Detection and diagnosis

Bundled rules now include complete RQ saturation, missing Gunicorn capacity,
failed/stopped bench services, sustained CPU/memory/swap pressure, and slow
responses in addition to server, disk, site, queue, and stream health. The
active-state table remains a small evaluator working set. A new incident table
retains every fire/recovery episode, target labels, severity, value, start,
resolution, notification, and duration data for the Incidents UI.

The new Log Explorer searches across server, bench, site, log type, message
text, and the global time window. It supports live/pause behavior, result
limits, and export. Incident and site views link directly into related log
scope.

## UI information architecture

The old mixed configuration/operations dashboard was replaced with a focused
monitoring shell:

1. fleet overview and attention queue;
2. searchable server inventory and host telemetry;
3. benches with worker capacity, queues, services, and process evidence;
4. site health and history;
5. global searchable logs;
6. active and historical incidents.

The layout uses a compact desktop sidebar, mobile bottom navigation, consistent
status language, responsive tables/cards, accessible focus states, and a shared
timeline. Destructive or remote operational affordances are absent.

## Known observability limit

Exact web-request occupancy needs an application/server instrumentation source
such as Gunicorn StatsD, an Nginx status endpoint, or a Frappe request hook.
Enabling one would change the target configuration, so it is intentionally not
done by this read-only monitor. The current console provides configured versus
running web capacity, process utilization, response latency, queue state, and
logs without crossing that boundary.
