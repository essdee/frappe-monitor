# Full-stack architecture and code review

Date: 2026-08-13  
Branch reviewed and repaired: `main`

## Outcome

The central architecture is viable and was retained: one monitor process pulls
bounded metrics over SSH, writes time series to VictoriaMetrics, streams
explicitly selected logs to Loki, keeps operational state in SQLite, evaluates
alerts centrally, and serves the Vue dashboard. A full rewrite would have added
risk without removing the real bottlenecks.

The original implementation was not production-safe. Its main problems were
loss-prone log cursor semantics, overlapping and stale collection behavior,
false alert transitions, insecure SSH trust, weak HTTP/auth boundaries,
unbounded outage buffering, query fan-out proportional to failed sites, and
frontend polling races. Those defects were repaired in place and the obsolete
second log-ingestion path was removed.

## Findings and disposition

| Severity | Area | Finding | Disposition |
|---|---|---|---|
| Critical | Live logs | Relative line offsets could skip or duplicate data after reconnect, truncation, or rotation. Loki and cursor commits were not one ordered operation. | Replaced with a versioned absolute byte cursor plus file identity, explicit rotation/truncation events, serialized push/commit, reconnect restoration, and protocol validation. |
| Critical | Live logs | A Loki outage allowed queued lines to grow without a hard bound. | `max_batch_lines` is now a hard per-stream limit. Failed pushes apply SSH/TCP backpressure; uncommitted bytes remain on the remote file. |
| Critical | SSH | Host keys were not enforced strongly enough, and dial/handshake cancellation and IPv6 addresses were inconsistent. | Strict `known_hosts`, typed host-key failures, cancellable TCP/SSH handshakes, IPv6-safe addresses, cached keys, bounded command output, and per-host session limits. |
| High | Alerts | Missing telemetry during a server outage could be announced as recovery for site, disk, Redis, or stream alerts. Deleted/renamed servers could also generate false recoveries. | Recovery now requires a fresh positive reachability metric and, when available, a reachable registry state. Unknown probes and evidence failures defer recovery; unmanaged state is silently pruned. |
| High | Alerts | Notification cooldown advanced even when Telegram delivery failed; recovery state could be deleted before delivery; partial multi-chat retry duplicated successful recipients. | Cooldown advances only after success, failed fire/recovery delivery remains retryable, and process-local per-chat receipts retry only failed targets. |
| High | Alerts / scale | Site alert details performed three VictoriaMetrics queries per failed site. | Companion metrics are fetched once (concurrently) and joined by server/bench/site in memory, so query count is constant with outage size. |
| High | Scheduler | Slow pulls could overlap for the same server, startup waited a full cadence, and timeouts were inconsistent with inner SSH/push deadlines. | Per-server overlap guard, global parallel cap, immediate startup/deploy collection, cancellation-aware stop, cadence-aware lookback, and cross-field timeout validation. |
| High | Site monitoring | Serial probes exceeded SSH deadlines and produced torn collector output; skipped probes could look healthy or unhealthy instead of unknown. | Bounded worker pool, whole-phase safety budget, complete output for every discovered site, explicit `-1` unknown health, and stable failure reason codes. |
| High | Server lifecycle | Child snapshots, cursors, and alert state could outlive a deleted server; retained TSDB samples could resurrect it in alerting. | Database cascade edges, migration coverage, scheduler/stream removal hooks, label cleanup, and registry-filtered alert samples. |
| High | Authentication | Forwarding headers were trusted too broadly, login attempts were not safely bounded, and auth-disabled logout could strand the SPA on an unusable login form. | Explicit trusted proxy CIDRs, right-to-left forwarded-IP parsing, bounded throttling buckets, signed HttpOnly cookies, Basic API compatibility, auth-mode discovery, and correct logout behavior. |
| Medium | API | JSON mutations accepted large/ambiguous bodies and weak server identifiers; duplicate names made metric labels collide. | Body caps, unknown-field rejection, single-document decoding, canonical field validation, unique normalized names, and legacy duplicate repair. |
| Medium | Frontend | Interval polling overlapped requests; late route/range responses overwrote current state; labels were interpolated unsafely; nanosecond timestamps lost precision. | Completion-based coalesced polling, generation guards, centralized 401/error handling, safe query literal construction, and BigInt Loki timestamps. |
| Medium | Frontend | Health UI collapsed unknown into failure and claimed an empty alert list proved the whole system healthy. | Explicit unknown rendering and accurate alert-disabled/no-firing language. |
| Medium | Deployment | Only one remote script was deployed reliably, first collection could run before deployment, startup success was logged before HTTP bind, and `make run` pointed at a missing config. | Atomic dual-script deployment, first pull after deployment, hot stream restart, bind-before-ready lifecycle, shutdown draining, and tracked example config. |
| Medium | Maintainability | Two competing log ingestion implementations existed; comments, versions, examples, and guides described different systems. | Removed the unused offset-only log tailer and rewrote the evergreen architecture/config/API/deployment/operations documentation around the actual runtime. |

## Resulting runtime boundaries

1. The scheduler owns short, bounded metric pulls. One server cannot overlap
   itself, and global concurrency prevents a large fleet from stampeding the
   monitor or bench hosts.
2. The streamer owns long-lived SSH sessions separately from metric pulls.
   File identity and committed byte offsets are durable; Loki outages stop
   source consumption at the configured memory bound.
3. VictoriaMetrics and Loki remain the telemetry stores. SQLite holds only
   registry data, snapshots, alert state, and committed log cursors.
4. Alert evaluation is transition-based. Disappearance is not treated as
   recovery without positive reachability evidence.
5. The SPA is a read/query client plus server-management UI. It does not run
   independent overlapping poll loops or construct unescaped label selectors.

skipped its container-backed VictoriaMetrics/Loki stages. `systemd-analyze

with the same flags as the bundled Compose service, so the metrics path has now
also been exercised against a real TSDB. Loki remained outside that metrics-only
follow-up.

## Remaining limits

The remaining non-blocking engineering risks and deliberately deferred product
scope are tracked in [`../hardening-backlog.md`](../hardening-backlog.md). The
most important production follow-ups are repository CI, a disposable real-SSH
integration test, versioned database migrations before any destructive schema
change, and an optional disk-backed log spool if the simultaneous
Loki-outage/monitor-crash/remote-rotation case must be lossless.
