# Site observability product plan

## Product goal

Frappe Monitor is a lightweight, read-only observability control plane for
multiple Linux servers, Frappe benches, and sites. It connects over SSH,
collects bounded telemetry, and presents an operator-focused web UI and
Telegram alerts. It does not deploy code, pull repositories, restart services,
or mutate a monitored host.

## Architecture decision

Keep the current central Go service, SQLite control state, VictoriaMetrics time
series, Loki logs, and Vue UI. Replacing this with a full OpenTelemetry stack or
installing an agent on every host would add operational cost without solving
the Frappe-specific discovery and correlation problem.

The product uses two diagnostic levels:

1. Continuous, low-overhead telemetry: SSH host/bench/service metrics, health
   probes, Frappe's native `monitor.json.log`, application logs, and database
   slow-query logs where the SSH account can read them.
2. Temporary deep diagnosis: Frappe Recorder data may be inspected when an
   operator has enabled it outside Frappe Monitor. Recorder is not enabled or
   run continuously because Frappe documents its sizable runtime overhead.

Frappe's native monitor is the primary per-site source. It records requests and
jobs with the site, timestamp, duration, request path/status/response size or
job method/wait, and a request UUID. The UUID also appears as
`FRAPPE_TRACE_ID` in SQL comments while monitoring is active, allowing the
slow-query parser and log explorer to correlate database events with a request. The monitor
detects whether the native setting is enabled but never changes it.

MariaDB/MySQL multi-line slow logs and common PostgreSQL duration records are
parsed incrementally with a 64 KiB statement-state limit. Database/user names
are SHA-256 hashed on the monitored host and truncated to a 96-bit equality
identity. Only the hash is emitted, so site metrics can join to host-level
database events without exposing tenant database names. Exact SQL remains in
the original Loki stream; a second site-correlatable summary contains duration,
lock time, rows, engine, operation, and an optional trace ID but no SQL.

## Cardinality and resource limits

- Request UUIDs, IP addresses, document names, users, query text, exception
  messages, and raw URLs never become time-series labels.
- Document routes are normalized to `:name`; arbitrary website routes collapse
  to `/_web`. Raw values remain searchable in Loki.
- Aggregate duration series are one series per site so rolling p95 remains
  accurate and cheap. Route-level series are separate and capped in the UI.
- SSH collection, site probes, streaming buffers, push batches, request
  timeouts, UI query ranges, and displayed route counts are bounded.
- A native monitor event cursor advances only after its raw Loki record and
  derived VictoriaMetrics samples both succeed. Stable source timestamps and a
  byte-offset suffix make retries idempotent.
- Test browsers, preview servers, and subprocesses must be terminated when a
  test ends. Integration commands use explicit timeouts.

## Delivery phases

### 1. Site request/job foundation

- Discover and stream `logs/monitor.json.log`.
- Parse current nested Frappe request/job JSON plus older flat records.
- Store raw events in Loki and bounded-cardinality samples in VictoriaMetrics.
- Report native monitor readiness in collection/API/UI.
- Show requests/min, request p95, HTTP error rate, job p95, and busiest routes.
- Add default Telegram rules for request p95, HTTP 5xx rate, and job wait p95.

### 2. Correlated investigation

- [x] Site-scoped log search across bench-level and site-level streams.
- [x] Request UUID search across every server log.
- [x] MariaDB/PostgreSQL slow-query parsing with private database-to-site mapping.
- [x] Correlated slow-query summaries and `FRAPPE_TRACE_ID` search.
- [x] Error grouping by exception type without putting messages in metric labels.

### 3. Capacity and incidents

- [x] Worker saturation and queue wait timelines.
- [x] Bench capacity view combining configured/running workers, RQ activity,
  service RSS/CPU, request load, and failures.
- [x] Durable incident timeline with firing/recovery evidence and deep links.
- [x] UI-configurable thresholds, rule validation, and Telegram routing.

### 4. Production hardening

- [x] Retention and storage-budget controls.
- [x] Backpressure visibility and a backend-independent runtime status card.
- [x] Installer, update, backup, automatic rollback, and diagnostic workflows.
- [x] Go, UI, script, integration, responsive-browser, restart, and outage tests.

## Measurement boundary

Standard Frappe Gunicorn workers can serve several sites from the same process.
Agentless process inspection therefore cannot truthfully attribute worker CPU
or RSS to an individual site. Frappe Monitor will show exact host/bench/process
resources and exact per-site request duration/volume/errors. Exact per-request
CPU or memory attribution would require additional in-process instrumentation
or per-site process/cgroup isolation and is not claimed by this design.

## Local validation snapshot

On 2026-08-14 the read-only collector was run directly against
`/mnt/storage/dev/frappe-v16`: one bench and five sites were discovered, all
five internal health probes succeeded, every emitted database identity passed
the strict hash format check, Redis reported one registered idle RQ worker, and
the complete service inventory was captured. Native monitor telemetry was
disabled for all five sites and no readable slow-query log was present, so
those two live feeds were correctly shown as unavailable rather than populated
with invented data. Parser, sink, API, alert, collector-integration, web unit,
type-check, and production-build tests cover those feeds with deterministic
fixtures.
