# Telegram Alerting — v1 Decisions

**Date:** 2026-04-29
**Amends:** `docs/2026-04-22/1.md` §9 ("The Alert System") — Notification channels: Telegram

The master plan's §9 mentions Telegram with multiple chat IDs ("personal, team channel, per-client") and per-rule recipient overrides. For v1, those nuances are deferred. The simpler design below is the source of truth.

## Decisions

### Bot model

- **Single bot.** One Telegram bot, created via `@BotFather`. Its token is stored as a config secret (env var `TELEGRAM_BOT_TOKEN`).
- **Admin-managed recipient list.** The administrator (the operator running frappe-monitor) maintains the list of chat IDs that should receive alerts. Recipients do not self-enroll.
- **No inbound interaction.** The Go binary only calls Telegram's `sendMessage` API. It does not run a `getUpdates` loop, does not register a webhook, and does not parse any incoming message. Telegram interaction is one-way: monitor → user.

### Routing

- **Fan-out to all.** When an alert fires, the message is sent to **every** configured chat ID. There is no per-rule recipient filtering, no severity-to-recipient mapping, and no scope-based routing in v1.
- The master plan's "Personal / team / per-client" recipient model and "per-rule notification overrides" are explicitly **deferred** — not implemented in Phase 6.

### What this enables

- The notifier component is essentially `(botToken, chatIDs []string)` + a single `Send(message string)` method that loops over `chatIDs` and POSTs to Telegram.
- Configuration UI in the dashboard: one text field for the bot token, one editable list of chat IDs.
- No background polling, no inbound state machine, no pairing flow.

### What we lose

- Different stakeholders cannot subscribe to different alert subsets — e.g. a per-client alert routing model is not supported. If/when that's needed, it becomes a Phase 6.5 follow-up: introduce a `recipients` table linking chat IDs to alert rules.

## Implementation impact

When Phase 6 (alerting) starts:

1. Update master plan §9 to reflect this simpler model (or link to this doc).
2. Implement `internal/notify/telegram.go` with `TelegramNotifier{ Token string; ChatIDs []string }` and a `Send(ctx, message)` that fans out.
3. SQLite schema: add a `notification_channels` row for Telegram (token + chat IDs as JSON column). No relationship table to alert rules.
4. Dashboard: a single "Telegram" panel under Settings with the bot token field + chat ID list editor.

## Why we chose this

The user explicitly asked for the simplest possible Telegram delivery and pushed back on additional design discussion. v1 ships fast; if more sophisticated routing is ever needed, the `Store` interface and notifier abstraction make it straightforward to add.
