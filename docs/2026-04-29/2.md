# Development Workflow — Branching & Review Loop

**Date:** 2026-04-29
**Scope:** All implementation work on this repository.

## Git branching model

```
main          ← production-ready code (only merged from develop)
└── develop   ← integration branch (all features merge here)
    └── feat/<scope>-<slug>   ← per-feature branches; PR into develop
```

### Rules

- **`main`** is the production branch. Never commit feature work directly to `main`.
- **`develop`** is the integration branch. All feature branches PR into `develop`. The user merges PRs **manually** via the GitHub UI — automation does not perform merges.
- **Feature branches** are named `feat/<scope>-<slug>` (e.g. `feat/phase-1-foundation`). Each phase or self-contained change gets its own feature branch.
- **Remote:** `origin` = `git@github.com:essdee/frappe-monitor.git`.

### Initial state (2026-04-29)

After `git init`, the initial commit on `main` was the docs/2026-04-22 design plans. `develop` was branched from that commit; `feat/phase-1-foundation` was branched from `develop`. All Phase 1 implementation commits land on the feature branch.

## Per-task review loop

Phase 1 (and likely subsequent phases) is executed task-by-task with a separate reviewer terminal between worker and user. Handoff is via a local `tasks/` folder at the repo root, gitignored.

### Files

- **Worker writes:** `tasks/task-{N}-{slug}.md`
  - Plan ref (e.g. `docs/2026-04-22/2.md §Task 3`)
  - Branch + commit SHA
  - Files changed
  - Tests run (command + result)
  - Notes / deviations from plan
- **Reviewer writes:** `tasks/task-{N}-{slug}.result.md`
  - **First line is `PASS` or `FAIL`** (machine-readable).
  - Comments below.

### Loop

1. Worker completes a task, writes `task-N-<slug>.md`, signals "ready for review", stops.
2. User triggers the reviewer terminal.
3. Reviewer writes `task-N-<slug>.result.md` with verdict.
4. Worker reads first line of result file:
   - `PASS` → delete result file, mark task complete, proceed to next task.
   - `FAIL` → address comments, update `task-N-<slug>.md`, delete result file, signal re-review.
5. Repeat until `PASS`.

## Why

- Per-task review keeps each commit independently understandable.
- Manual PR merges keep a human in the loop on every integration into `develop`.
- The `tasks/` folder is gitignored because it's a workflow artifact, not part of the codebase. Only `.gitignore` and `tasks/README.md` (documenting the convention) live in git history.

## Documentation convention (this folder)

Project decisions, design changes, and significant conversations are captured in `docs/YYYY-MM-DD/N.md` — one date folder per day, sequentially numbered files within. Examples:

- `docs/2026-04-22/1.md` — original master plan
- `docs/2026-04-22/2.md` — Phase 1 implementation plan
- `docs/2026-04-29/1.md` — Telegram alerting v1 decisions
- `docs/2026-04-29/2.md` — this document

This is preserved across the project so anyone reading later can reconstruct decision history.
