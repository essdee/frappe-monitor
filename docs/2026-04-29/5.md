# Phase 4 — Dashboard Foundation

**Goal:** Operator can open the binary's URL in a browser and see live CPU/memory/disk/load graphs for each registered server, driven by a URL-synced timeline filter. Metrics flow from VictoriaMetrics through a thin Go proxy.

**Branch:** continue on `feat/phase-2-server-metrics` (single working branch).

**Phase milestone:** start the binary + VM, register a server, wait for one pull cycle, open `http://localhost:8080/` in a browser, see the server in the overview grid, click in, observe four live graphs that respond to the timeline filter.

---

## Deliverables (10 tasks)

| # | Task | Brief |
|---|---|---|
| 1 | **Frontend scaffold** | `web/` directory: Vue 3 + Vite + TypeScript + vue-router + ECharts + a small fetch wrapper. `npm run build` produces `web/dist/`. |
| 2 | **`//go:embed` wiring** | New `internal/web` package with the embed directive. chi router mounts an SPA fallback handler at `/*` that serves `index.html` for unknown paths so client-side routing works. Static assets served with proper cache headers. |
| 3 | **Backend metrics proxy** | `GET /api/v1/metrics/query?q=<promql>&from=&to=&step=` → forwards to VM's `/api/v1/query_range`. Validates query params; returns the VM body verbatim with our content-type. |
| 4 | **Backend logs proxy** | `GET /api/v1/logs/query?q=<logql>&from=&to=&limit=` → forwards to Loki's `/loki/api/v1/query_range`. Same validation pattern. |
| 5 | **Timeline filter component** | Shared `TimelineFilter.vue` — quick presets (15m / 1h / 6h / 24h / 7d / 30d) + custom datetime + refresh-interval (off / 30s / 1m / 5m). State synced to query params (`?from=&to=&step=&refresh=`). |
| 6 | **API client + composables** | `web/src/api.ts` typed wrappers around `/api/v1/{servers,metrics,logs}`; Vue composables `useServers()`, `useMetricsRange(query, range)` returning ref-based data + loading + error. |
| 7 | **Servers overview page** | `/servers` — grid of `ServerCard.vue`. Each card shows status dot, name, hostname, current CPU%/mem%/disk%, last-pinged-at relative time. Sorted worst-first by status then CPU%. Auto-refreshes per the timeline component's interval. |
| 8 | **Server detail page** | `/servers/:id` — header with server metadata + status; four ECharts time-series (CPU%, memory %, disk-used per mount, load 1/5/15). All fed from `/api/v1/metrics/query` for the URL-synced range. |
| 9 | **Layout shell** | `App.vue` with sidebar nav (Servers — others stubbed for Phase 5+), header with timeline filter, main content slot. Light/dark theme via CSS variables (system-pref default). |
| 10 | **Smoke + Phase 4 acceptance** | Extend `scripts/smoke.sh`: assert `web/dist/index.html` is in the binary (via curl `/`), assert `/api/v1/metrics/query` proxies cleanly to VM, assert the SPA fallback returns `index.html` for `/servers/123`. Build target `make web-build` runs Vite before `make build`. |

## Open design notes (refine while coding)

- **PromQL we actually need for Phase 4 graphs:**
  - CPU%: `100 * (1 - rate(frappe_server_cpu_idle[5m]) / clamp_min(sum without (mode) (rate(frappe_server_cpu_user[5m]) + rate(frappe_server_cpu_nice[5m]) + ... ), 1))` — or simpler: emit a derived "cpu_total_jiffies" once we add a percentage helper. For Phase 4 v1, compute client-side from raw counters (rate over selected window).
  - Memory %: `100 * (1 - frappe_server_mem_available_bytes / frappe_server_mem_total_bytes)`.
  - Disk %: `100 * frappe_server_disk_used_bytes / frappe_server_disk_total_bytes` (group by mount).
  - Load avg: raw `frappe_server_load_1m{server="..."}` etc.
- **Auto-refresh strategy**: setInterval on the composable level with cleanup in `onScopeDispose`. No SSE / websockets in Phase 4 — polling is enough at 30s+ intervals.
- **Build pipeline**: Phase 4 makes the Go binary depend on Vite output. `make build` should fail loudly if `web/dist/index.html` is missing rather than embedding a placeholder. A `web/dist/.placeholder` committed file lets the embed compile during early-phase development before `npm run build` runs successfully.
